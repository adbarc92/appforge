## What this session changed (and why it matters)

The branch was picked up **red** — `test_answer_loop_advances_through_questions_to_prd` was failing. Root cause and fixes:

1. **Two colliding pause mechanisms (`3ed3e20`).** Commit `16bc6a7` added an `AsyncSqliteSaver`, which auto-activated `interrupt_before=["product_owner_approval"]` in `graph.py`. But the orchestrator still used the Slice-3 node-blocking future (`_await_resume`). `interrupt_before` returns from `ainvoke` *before* the node body runs, so the resume future was never armed and every clarifying answer was dropped (loop died after question #1).
   - **Fix:** completed the planned migration — `graph.py` drops `interrupt_before`; `approval_node` pauses via the dynamic `interrupt()` helper; the driver loops over `ainvoke`, detects the `__interrupt__` key, and resumes with `Command(resume=decision)`.
2. **Resume hand-off race (`3ed3e20`).** With multiple `ainvoke` calls, a user decision could land after the previous resume future resolved but before the driver re-armed, and get dropped — the loop stalled after the *second* answer.
   - **Fix:** replaced the single resume future with a **per-project `asyncio.Queue`** so an early-arriving decision is buffered, not lost. Deterministic 5/5 on the previously flaky test.
3. **`approval_count` conflation (`6f80025`).** The answer-gathering branch bumped `approval_count` once per clarifying answer, so escalation (`approval_count >= 3`) fired on the *first* rejection.
   - **Fix:** `approval_count` now counts PRD rejection cycles only; answering a question routes back via `approval_status` without incrementing it.

Also added: `approve`/`reject`/`modify`/`retry` orchestrator methods + Socket.IO handlers; `load_project` hydration emit; approval-flow, rejection-cycle, socket-load, and E2E tests.

## Design notes for the next session

- **The approval gate is a single interrupt point that does double duty.** During clarification `approval_node` treats the resume value as the answer to the latest question (routes back via `approval_status="rejected"`); once `state.prd` is set, the same interrupt becomes the real approve/reject/modify gate. `approval_required` is emitted from `clarifying_node` (only when a PRD exists), **not** from `approval_node` — so don't add an emit before `interrupt()` (the node re-runs from the top on resume and would double-emit).
- **Resume delivery is queue-based, not future-based.** `resume()` enqueues; the driver dequeues. This is deliberate (see race fix above) — don't revert to a single future.
- **The saver is re-opened per event loop.** `aiosqlite` connections bind to the loop they were opened on; the orchestrator is a module-level singleton in `backend.main`, and tests create a fresh loop per test, so `_ensure_saver` detects a loop swap and re-opens. Keep this.

## Known limitation: browser-reload hydration is partial

`load_project` emits `orchestrator.load()` = the raw `ProjectState.model_dump()` (`idea`, `questions`, `answers`, `prd`, `approval_status`, …). The frontend's `hydrateFromState` expects a `ProjectStateSnapshot` (`project_id`, `messages`, `agents`, `budget`, `phase`, `prd`, `status`). The shapes don't match, and the checkpoint stores **no chat transcript**, so reload can restore PRD/phase/agent-ish state but not the message history. Reconciling this (a backend-side snapshot adapter + deciding what to do about the missing transcript) is the first real follow-up — it's the genuine fix for the "reload resets UI" limitation the prior status doc anticipated.
